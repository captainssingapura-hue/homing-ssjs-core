# Release 0.7.0 — Keyboard Panes, One Tab Budget

The workspace's split panes become **operable from the keyboard** — arrow
between panes, enter a widget, and hand focus back — and the per-pane tab limit
collapses into a **single workspace budget** that means what it says. Two RFCs
land: **RFC 0048** (modal keyboard pane navigation) and **RFC 0047** (global tab
budget). Both change how the workspace behaves — see **Breaking changes** below.

## What's in the box

### Modal keyboard pane navigation (RFC 0048)

Switching pane focus used to require the mouse — the click-capturing cover
overlay was the only way in. The workspace now has a **two-mode keyboard model**,
and the mode split is the whole trick: because the widget isn't receiving keys in
shallow mode, plain **Arrows / Enter / Tab** are unambiguous — no modifier
gymnastics, no editable-guards.

| Mode | Who owns the keyboard | Keys |
|------|----------------------|------|
| **Shallow** (select) | the workspace chrome | Arrows move a pane **cursor**; **Tab** cycles tabs *within* the selected pane, never leaving it; **Enter** / double-click enters deep |
| **Deep** (interact) | the entered widget, exclusively | everything — the widget gets keys raw; it returns to shallow through the give-up layer |

It reuses the machinery already there: the **cover overlay** (cover on =
shallow/select, the widget inert to stray input; cover off = deep/interact) and
the single workspace-active-tab model. `mode()` is *derived* from the
workspace-active tab — there's no separate mode flag to drift.

| Piece | Role |
|------|------|
| **Shallow / deep rings** | The selected pane wears a dimmer *selection* ring; the entered pane wears a brighter *entered* ring. Both are drawn on a `z-7 ::after` overlay so they sit **above** the cover and the widget, not under them. |
| **Shared-edge arrow move** | Directional moves collect the panes sharing the pressed divider with positive perpendicular overlap, then pick nearest-gap → max-overlap. It's **stateless** — the tie-break is geometric, with no cross-axis focus memory — so the same layout always moves the same way. Specified with a short proof in the RFC. |
| `FocusScope` — the give-up layer | A portable DOM **convention**, not an injected API: an un-consumed **Escape** (or a `homing-focus` release event) bubbles to the entered pane's own content element and drops it back to shallow. A widget that *uses* Escape keeps it (`stopPropagation`); a terminal-like widget that owns Escape entirely offers its own shortcut that `dispatchEvent`s the release. |
| `enterDeep` — one entry point | Every deep-select — arrow-Enter, a click, the picker's `+`, focusing an existing singleton — routes through `enterDeep`, which activates the pane **and** attaches the give-up layer. There's exactly one place a pane becomes entered. |
| **Focusable content states** | Picker tiles, the "Loading …" placeholders, and the "(empty pane)" filler now carry `tabindex`/`role`, and `.hmtp-content` is `tabindex=-1`. A click or deep-enter lands focus *inside* the pane rather than on `<body>`, so Escape always has somewhere to bubble from. |

### One shared tab budget (RFC 0047)

The workspace always had one conserved tab budget (default 16), but
`MultiTabPane` **rationed it per-pane by depth** — `capacity = floor(budget /
2^depth)` — so splitting a pane halved its children's caps and the limit a user
hit shifted as they reshaped the layout. The number was meaningless at the
workspace level, which is exactly where the resource it guards lives.

Rationing is now a **single shared pool**: an add is allowed iff *total tabs
across all slots < budget*. The depth division is gone.

| Piece | Role |
|------|------|
| **Pool predicates** | `totalTabs()` / `budget()` / `atCapacity()` / `canAdd()` replace the per-pane `capacityOf(slotId)`. The limit is a workspace total, so the predicates are pane-independent. |
| **The `+` disables together** | At the pool limit every strip's `+` greys out at once — the affordance now tells the truth about a workspace-level resource, not a pane-level artifact. |
| **Splitting is free** | A split adds no tabs, so it can't breach the budget and never shrinks anything — the conservation invariant holds structurally, with no gate. Pinned widgets count like any other tab. |
| **Per-`WorkspaceSpec` knob** | The budget is a workspace property you set once on the spec, not a number the layout derives. |

Refuse-at-cap — the add is declined (disable `+` / throw); **no eviction in v1**.

## Breaking changes

This release **changes workspace behavior** and the `MultiTabPaneContract`
surface. There is a single built-in `MultiTabPane` implementation, updated here;
downstream code that *drives* the pane or implements the contract should note:

- **`capacityOf(slotId)` is removed** (RFC 0047). Use the pool predicates —
  `totalTabs()`, `budget()`, `atCapacity()`, `canAdd()`. Per-pane capacity no
  longer exists as a concept.
- **Boot is now shallow.** No tab is workspace-active at boot; the pinned spawner
  adds its tabs but no longer auto-activates the first one. A pane becomes
  *entered* only through a deliberate deep-select. Downstream that assumed a live
  widget immediately on boot will see the difference (the workspace shell forces
  shallow on restore, and `PinnedTabSpawnerTest` asserts the shallow boot).
- **New contract methods.** `MultiTabPaneContract` gains `selectPane`,
  `focusPane`, `cycleTabInPane`, `enterDeep`, `releaseToShallow` (commands) and
  `totalTabs`, `budget`, `atCapacity`, `canAdd`, `mode`, `selectedSlot`
  (read-only). Additive for *callers*; a custom implementer must supply them.

## Known limitations

- **Arrow navigation is stateless by design.** There's no memory of where you
  entered a pane from, so a move out and back can land on a different neighbour
  than you left — the trade for a predictable, layout-only rule (cross-axis focus
  memory was considered and rejected).
- **The widget picker isn't arrow-navigable yet.** Its tiles are focusable and
  Tab reaches them, but arrow/Enter selection *within* the launcher is still to
  come (Wish 0002, piece 4) — the end goal is a fully keyboard-operable
  workspace, and this is the last mile.
- **The give-up layer is a convention, not enforcement.** A widget that swallows
  Escape without re-emitting — and offers no release shortcut of its own — can't
  be handed back by keyboard. That's the widget's contract to keep, not the
  workspace's to police.
- **Refuse-at-cap, no eviction.** At the budget the workspace simply declines the
  add; it never closes an existing tab to make room. Eviction can follow later.
- **The modal keeps its mouse-first design.** Keyboard pane navigation is a
  workspace feature; the modal is unchanged.
