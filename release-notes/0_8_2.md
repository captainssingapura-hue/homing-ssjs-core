# Release 0.8.2 — One Markdown Path, and Three Places the Keyboard Was Missing

A release about **surfaces that only looked like they behaved the same**. The
studio had two markdown readers and they had quietly diverged: diagrams reached
one, a scroll-synced TOC reached the other, and neither gap was visible from the
side you were standing on. Three trees ate `Alt+Left` while the reader beside
them did not. A pane's tab strip was not part of its pane.

**RFC 0059 Phases 2 and 3** end the divergence: markdown is normalised on the
server and every reader renders the same tree, so a feature now lands once. The
bespoke `DocReaderRenderer` — 471 lines, over the effective-line cap, carrying 54
baselined findings — is gone.

The rest is keyboard and pointer: browser shortcuts stop being swallowed by
trees, the standalone reader gains the TOC keyboard it never had, and an MTP's
chrome bar starts belonging to its pane.

See **Breaking changes** — a module changed package, an app changed superclass,
a sealed interface gained a permit, and markdown anchors changed shape.

## What's in the box

### One markdown path (RFC 0059, Phases 2 and 3)

Two pipelines rendered markdown. `DocReader` fetched raw bytes, handed the whole
document to `marked`, then swept the resulting DOM for headings to build a TOC
and for `language-mermaid` fences to draw diagrams. Everything downstream of the
rigid pipeline got a code listing where the author had written a diagram.

**The change is upstream.** `MarkdownDocNormalizer` now splits fenced blocks into
typed `code` segments carrying their `language`, so *"is this a diagram?"* is a
question about **data**, answered before any DOM exists. No `querySelectorAll`,
no scan, and the presence gate is free.

| Piece | Role |
|------|------|
| **`MermaidPlateModule`** | Builds the fence first and renders over it, in its own sub-branch — so a successful render retires the fence with one `dissolveBranch` and no manual detaching. Lazy import, so a diagram-free doc never touches the network; one CDN seam; and on failure the source stays visible with a line saying which failure it was. |
| **`st_mermaid`** | Mermaid draws dark ink on a transparent ground and never hears about the theme, so on a dark one the diagram was unreadable. The plate mixes a light ground from `--color-surface` — with `var(--color-surface, white)` as a load-bearing fallback, because an undefined token makes the whole `color-mix` invalid and the plate would go *transparent* exactly when a theme is already broken. |
| **`DocReader` is now a shell** | A `SingleWidgetMPA` over `DocTreeWidget`, the same widget `doc-tree-viewer` hosts. Same `simpleName`, same `?doc=<uuid>`, same `Params`, `CODEC` and `AppLink` — which matters, because 168 catalogue entries across four repositories name `DocReader.INSTANCE` and address it with `doc`. |
| **`DocRefsModule`** | The References section and the category chip, lifted out of the retired renderer. 159 of the self-studio's 171 docs declare at least one reference, so this was never droppable — and living in its own module it lands once, for every reader that renders a doc tree. |

**The phase was gated on an inventory, not on enthusiasm**, and the inventory was
filled in against a running studio rather than from reading. Two features moved
(References, the category chip), two the rigid path already had or had better
(the export pill; real ids and `href="#<name-path>"` in place of inline `onclick`,
which need no JavaScript at all). And the question underneath: **all 177 uuids
were requested through both endpoints — 169 answer `/doc`, and all 169 also
answer `/doc-tree`.** Nothing the reader could serve was left behind.

What the reader gained by the swap: keyboard TOC navigation with scroll-sync,
mermaid, h4–h6 as navigable nodes, and section anchors that survive an export.

**Markdown docs are now name-addressed.** Each node is named by its heading's
slug, so a section's address survives its siblings being edited — and an anchor
written against the standalone reader still lands. `DocAnchor` names the scheme
once, in Java, where two implementations in two languages had been agreeing by
hand.

**A heading is a label, and the cap is a conformance rule.** The first draft of
the RFC called long headings "ordinary" and clipped them. That was wrong twice
over: a heading is a label, and a clipped slug still *looks* like a real anchor,
so nothing tells a reader it was silently shortened. `DocConformanceTest` now
fails any markdown doc with a heading over 40 slug characters, naming each one,
and the rule asks `MarkdownDocNormalizer.overlongHeadings` — the very code that
does the naming — so gate and behaviour cannot drift. Overlong headings are named
`wording_digest`: 33 characters, an underscore, six hex of SHA-256 over the whole
slug. Stable (a function of that heading's text alone, so it does not move when a
sibling is renamed), honest (`_a3f9c1` cannot be mistaken for a slug), and
conspicuous, which is the point.

### `TypedCodeSegment` — the code segment's language, typed

A listing's language started as decoration: it became `class="language-X"`, a
hint for a highlighter the framework does not ship, and a typo cost nothing
anyone would notice. Phase 2 changed that. **`"mermaid"` is now load-bearing** —
it is the difference between a diagram and a code listing — and a free-form
String is the wrong shape for a value a renderer branches on.

```java
new CodeSegment(src, "java")                  // the String form
new TypedCodeSegment(src, CodeLanguage.JAVA)  // the typed form
.code(diagram, CodeLanguage.MERMAID)          // draws
```

The mirror is a **fact, not a convention**: `SegmentJson` has one code emitter and
both segments call it, so the two cannot drift, and a test asserts identical
output across the whole vocabulary. That is what makes migration a per-call-site
decision — swap the one argument when you touch a doc, leave the rest, and
nothing observable moves. No JavaScript changed to make this exist.

The vocabulary is measured, not invented: java (278), js/javascript (76), mermaid
(35), bash (19), css (9), xml (5), json (4), html (3), and one or two each of md,
svg, csv and text. Note **js and javascript — the same language spelled two ways,
55 times and 21 times, and nothing could tell.** `CodeLanguage.JAVASCRIPT` has one
tag, so a typed doc cannot do both.

`CodeSegment` keeps its String, and should: `MarkdownDocNormalizer` builds it from
a fence's info string, which is unbounded author input and genuinely a String at
that boundary. The two segments exist because the two sources really are
different — one parses what someone typed, the other is written in Java against a
known set.

### Trees stop eating the browser's shortcuts

`Alt+Left` did not go Back in the catalogue viewer or the tree doc viewer.
`TreeRenderer.handleKeydown` matched on `ev.key` alone, so **`Alt+ArrowLeft` *is*
`ArrowLeft`** to it: the tree answered "consumed", and a host that hears
"consumed" calls `preventDefault`. Two things went wrong rather than one — the
navigation was cancelled *and* a branch was folded that nobody asked to fold. A
wrong action rather than a missing one.

One guard fixes all six forwarders, because every one defers to that return
value: `CatalogueHostRenderer`, `CatalogueTreeViewRenderer`, `DocTreeRenderer`,
the theme picker (twice) and the workspace switcher. The first two are why it was
so visible — they listen on `document`, so the chord was eaten wherever focus
happened to be.

Declined: **alt, ctrl and meta**. `Shift` is not, because it is not a navigation
chord and a range-select would want it. This is the rule
`WorkspaceShallowKeyboard` and `FocusManager` already state, applied where it was
missing.

### The standalone reader gets the TOC keyboard it never had

Same doc, two readers, two behaviours: in the workspace Document pane you could
arrow through the TOC and the body followed; at `/cat/meta/ontology-first` you
could only click. The split was never workspace-versus-standalone — it was
`renderDocTree` versus a hand-rolled TOC that registered no keydown listener at
all.

**`TocSyncSecretary`** extracts the coordinator that `renderDocTree` had carried
inline since RFC 0043 — one authority, two writers, and the asymmetry that
navigation **scrolls** while the spy only **highlights**. Nothing in it was ever
tree-shaped: `key` is opaque, an index-key in one reader and a heading slug in the
next. Extracting it also makes the law testable, which the inline literal never
was.

**`attachTocSync`** gives the flat anchor TOC the three Actors the Secretary
coordinates — keyboard, scroll-spy, scroll — so the two readers now differ in what
they **draw** and not in how they behave. Three decisions worth naming: a **roving
tabindex**, because a forty-heading TOC was forty tab stops in front of the
document; **the cursor follows the spy**, not just the keyboard, since a cursor
left at section one while the highlight sits at five is a second opinion about
where the reader is; and the anchors **keep their inline `onclick`**, which
survives static export where a listener would not.

It is a new module rather than more of `DocReaderRenderer`, which was already over
the cap and baselined for it — and the baseline matches on source text, so growing
that file is how a fix earns new findings.

### The chrome bar belongs to its pane

A click on a `MultiTabPane`'s tab strip or corner did nothing, and hovering them
did worse than nothing. Both handlers asked `_slotOfContentTarget`, which requires
`closest(".hmtp-content")` — so a leaf's three siblings were read as "the pane"
and "not the pane", and the pane's own furniture fell outside it.

**The hover half was the sharper bug.** Reporting `slotId: null` does not merely
fail to register: the coordinator clears `_hoverSlot` and re-runs
`_syncPointerLive`, so under RFC 0052's `inert = !(deep || pointerLive)` the pane
**re-inerted** and dropped its hover ring while the pointer had never left it.
Moving the mouse straight up from the content onto that pane's own tab bar
revoked its liveness.

Two different widths, because the two axes ask different questions. **Hover** asks
where the pointer *is* — the whole leaf counts. **Press** is a deliberate entry —
only the chrome's *background* counts (strip, corner, and the budget pill, which
is a label rather than a control).

The exclusion is by **identity, not descent**: a chip, its `×`, the `+` and the
corner buttons are all descendants, so they are excluded structurally rather than
by a list that would rot as the chrome grows. It could **not** be left to their
own `stopPropagation` — `_onPanePress` is a capture listener on the container, so
it runs before any listener on the target. Their `stopPropagation` reads like
protection and provides none; a naive widening would have made `×` enter the pane
it was closing and made a chip fire entry twice.

## Fixes

**No carriage return may reach a segment body.** `MarkdownDocNormalizer` split the
document on `\n` and rejoined on `\n`, so every line of a CRLF file kept its
trailing CR and carried it into the segment it landed in. Nothing had noticed
because the only consumer was the standalone reader, which hands the whole
document to `marked` — and `marked` normalises line endings before it parses. The
rigid path parses the fences itself, so the CR arrived intact at whatever rendered
the segment, and Mermaid's parser rejects it outright: six diagrams in the RFC
0049 appendix failed with *"Parse error on line 7"* for no reason visible in the
source. Normalised once, before the split, so it holds for every segment kind.

**The synced-section highlight was blue on every theme.** `rgba(59,130,246,…)`
written inline — blue on Carbon, blue on Turbo C, blue on Forbidden City.
Invisible as a fault because the reader had only ever been looked at on light
themes, and the same mistake the Mermaid plate had. Mixed from `--color-accent`
now, at the opacities the hardcoded values used.

**`DocTreeRendererModule` was in the wrong crate.** It lived in `homing-core-js`
on the reasoning that an injected dispatch made it substrate. The dependency
argument held; the bill did not. From core-js it could not reach `StudioStyles`,
so it styled itself with `style.cssText` and baked colours, and carried thirteen
baselined findings for it. It bought dependency purity and paid in conformance. A
document reader is a studio concern, and studio-base is where studio concerns can
be written properly.

## Breaking changes

- **`DocTreeRendererModule` moved crate**, from
  `…homing.core.js.DocTreeRendererModule` to
  `…homing.studio.base.composed.DocTreeRendererModule`. A downstream module that
  imports it by class changes one import. Its consumers inside the framework were
  always above core-js, and nothing inside core-js ever depended on it.
- **`DocReaderRenderer` is removed** — both the Java module and its `.js`. Nothing
  outside `DocReader` imported it, but a studio that mounted `renderDocReader`
  directly must move to `DocTreeWidget`.
- **`DocReader` is a class, not a record.** It now extends `SingleWidgetMPA`.
  `INSTANCE`, `Params`, `CODEC`, `link()` and `title()` are unchanged, so every
  catalogue entry and `AppLink` survives untouched. **`brandLabel()` and
  `homeUrl()` are gone** — they were a back-compat net for `/brand` and a record
  cannot be subclassed, so nothing could have overridden them; the brand comes
  from `StudioBrand`.
- **`Listable` permits `TypedCodeSegment`.** An exhaustive `switch` over
  `Listable` or `Segment` in downstream code will no longer compile until it
  handles the new variant — the cost of a sealed hierarchy, paid deliberately.
- **Markdown doc anchors changed shape.** A markdown doc is served name-addressed
  now, so a node's id is its name-path (`doc-node-<slug>/<child-slug>`) rather
  than an index. In-page links written against heading slugs keep working — that
  is the point of the change — but a link saved against the old index-based id
  will not resolve.
- **`DocConformanceTest` gains a heading-cap test.** A studio that extends it will
  fail on any markdown doc with a heading over 40 slug characters, naming each
  offender. `Doc.headingCapExempt()` is defaulted `false` and grandfathers a doc
  that predates the rule — it is debt, not licence, and new docs must not use it.
- **`StudioVars` is unchanged**, but `StudioStyles` gains `st_mermaid`,
  `st_mermaid_note`, `st_doc_section_active` and `st_doc_category`. Additive.

## Known limitations

- **The grid half of RFC 0059 is not built.** Phase 1 — an articulated relation
  rendered on `RelationGrid`, and markdown pipe tables opting in to it — is
  blocked on a markdown-preserving cell and is the next piece of that RFC.
- **A `mermaid` fence inside a `.markdown(…)` segment does not draw**, only a
  `code` segment does. This is a decision (RFC 0059 D15), not a gap: a
  `.markdown` segment means raw markdown and is mainly for text, and a diagram is
  not text. Naming it at the point of authoring is both the type-safe answer and
  the natural-reading one.
- **`renderCodeSegment`'s output for non-mermaid fences has not been compared
  against `marked`'s.** D8 accepted that cost explicitly and the comparison is
  still owed.
- **Mermaid is verified in the doc-tree viewer and the standalone reader, not in
  the workspace Document pane.** It shares the segment renderer, so it should
  follow; "should" is not "was checked".
- **The doc conformance gate reaches 4 of 25 doc catalogues.**
  `StudioDocConformanceTest.docProviders()` names four, so RFCs, doctrines,
  wishes, defects, releases, meta and ontology are ungated — for the heading cap
  *and* for RFC 0004-ext1's managed-reference scan. On disk roughly 98 docs carry
  an over-long heading; the gate sees 17.
- **17 docs and 60 headings are grandfathered** under `headingCapExempt`.
- **32 Java-authored `.code(…, "…")` call sites still pass a String.** Migration
  is per-call-site by design; nothing is forced.
- **Six diagrams in the RFC 0049 appendix do not render**, and did not before this
  release either. `;` separates statements in a Mermaid sequence diagram, so
  `FMx->>FMx: inert ; blur ; setActive(false)` is a parse error. A content defect
  in that doc, not in the pipeline.
- **The MTP corner's split/merge affordance is unchanged** — this release made the
  chrome bar behave, not look different.

Built green: **896 tests, no failures, no errors, none skipped.** Conformance:
zero errors, all crates conformant, and the baseline drops from **833 lines to
783** — the retired renderer's 54 and the relocated tree renderer's 13 leave;
`DocReader` inherits the 10-line generated-shell block every MPA app already
carries.
