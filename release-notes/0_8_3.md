# Release 0.8.3 — The Theme Is the Reader's, and the Framework Can See Itself

A release about **where a choice lives, and who is allowed to look**. A theme was
a query parameter: the server read it, every link re-stamped it, and a shared
`?theme=carbon` link followed the reader through the whole studio, outranking
their own preference on every page until they reached a link nobody had built.
The DomOpsParty — the discipline every conformance rule enforces the use of —
had never been looked at directly; the only handle it offered was the one that
could dissolve the tree, so nothing could observe it safely. A workspace kind was
a catalogue leaf of its own, so a studio with six kinds had six positions and no
container. And three channels in the conformance engine quietly exempted
anything that looked like a primitive.

**RFC 0064** moves the theme to the client: a preference steward that remembers
an explicit pick in `localStorage` and resolves it in one order everywhere, a
CSS manager that loads a group's whole dependency tree in waves and **switches
themes without a reload**, and a workbench that shows the graph doing it.
**RFC 0063** gives the party a frozen `snapshot()` and a monitor built on it —
and the monitor's first spawn found a forked import chain that had been loading
every widget's modules twice. **RFC 0058 Phase 1** makes the workspace *group*
the unit of placement and a kind an anchor inside it. The conformance engine
stops granting exemptions by category, and holds its baseline to what it claims.

Two smaller things: the theme picker previews a live page in a frame instead of
swatches, and **Brutalist** — a theme that finds out how far CSS alone goes — is
the eleventh theme.

See **Breaking changes** — `CssGroup.cssImports()` is gone and every group that
overrides it will not compile; the server no longer reads `?theme=` or
`?locale=`; Jazz Drums and the SVG backdrops are removed; `WorkspaceSpec.group()`
is `section()`; and the conformance gate refuses three things it used to accept.

## What's in the box

### The theme is the reader's (RFC 0064)

The address had been acting as the memory of a choice, because there was no
other. **`PreferenceSteward`** is that memory now — the one module that goes to
`localStorage` for a preference — and it resolves any preference by name in one
order everywhere: **the address as this page's override, then the stored pick,
then the caller's fallback.** It keeps only explicit picks; the address never
writes the store, because following a link is viewing, not choosing.
`localStorage` rather than a cookie, because the server resolves no context so
nothing needs carrying to it, and `localStorage` is per origin *including the
port*, so two studios on one host keep separate choices. The key is
`homing.theme`, inspectable in DevTools, which RFC 0064 asks for.

**The steward splits by authority.** `PreferenceViewInstance` is what every
component holds — `preferred`, `override`, `resolve`, `onChange` — and a holder
of the view can ask and can listen and *cannot change anything*, by construction.
`PreferenceStewardInstance` is the writer — `remember`, `forget` — held only by
the surfaces that let a user choose. RFC 0063's observation-by-construction, one
layer over. A change notification carries nothing: a listener that wants details
goes to the view, so the one order of resolution stays in one place and a
listener cannot be handed a stale value. Another tab's pick arrives the same way,
through the `storage` event, filtered to our keys.

Four things stop, because the steward replaced what they were for:

| What stopped | Why |
|------|------|
| **The server reads `?theme=`.** | `AppHtmlGetAction` propagates the registry's default and nothing else. The address's `?theme=` is the client's to read, as the override the steward honours. Done first as a controlled break, to prove the server never needed the context and to show exactly what still read the address. |
| **`HrefManager` stamps session keys.** | It used to copy the page's `?theme=` and `?locale=` onto every internal link. `_SESSION_KEYS` and `_propagateSessionKeys` go entirely. An explicit `?theme=` an author writes *into* a link passes through untouched and wins for the page it names — the Themes page's Activate links, the preview frame. On `/cat?theme=carbon`, all 317 rendered links now carry neither. |
| **The module chain carries locale.** | The page template no longer reads `?locale=` or stamps `navigator.language` onto the module URL. `view.resolve("locale", navigator.language)` is the whole client-side rule. Nothing served varies by locale yet, which made this the cheap moment to settle where it lives. |
| **The Themes page parses the address.** | It marked *(active)* by reading `?theme=` — right under an override, wrong on a bare page under a stored pick. It asks the view now, and its three raw `window.location` reads leave the baseline. |

### CSS dependencies: declared per class, derived per group, loaded in waves

`CssClass.dependsOn()` names the classes a class's rules lean on — a class whose
body assumes another's is present on the same element or an ancestor, or that
must follow another's in the cascade to win at equal specificity. **Declared per
class, because that is where the knowledge is**: the author of `tp_body` knows it
lays out inside `md_split`; nobody else does.

```java
public record tp_body() implements CssClass<ThemePickerStyles> {
    @Override public List<CssClass<?>> dependsOn() {
        return List.of(new MasterDetailStyles.md_split(), new SystemDialogStyles.sd_body());
    }
}
```

A group's dependencies are **derived from that and never declared**.
`CssGroup.cssImports()` is removed; `CssImportsFor.of(group)` is the derivation —
first-mention order, self excluded, deduplicated by class. There is deliberately
no override point: a method a group could override could only restate the
derivation or disagree with it, and the disagreement that matters — declaring
nothing — would silence every `dependsOn()` added later. `CssGroup.prior()` marks
a group that predates the discipline and that everything leans on
(`StudioStyles`, `Util`): it declares nothing and loads before the graph, and a
prior with dependencies is refused. `CssGroupResolver` — declared long ago and
called by nothing — now refuses a cycle with the names on it, and runs when a
group module is served, so either fails on first use.

**Served as data, not as imports.** A served group module's `loadCss` call now
carries the group's transitive subgraph —
`{ "<group>": { deps: [...], prior } }` for the group and everything under it. A
dependency's *CSS* is needed; its handles are not; and a lazily mounted widget's
group must carry its whole tree so the client can load missing dependencies by
name.

The client side is one manager and three pure affiliates:

| Piece | Role |
|------|------|
| **`CssDependencyGraph`** | No DOM, no fetch, no theme. `merge()` folds subgraphs in as modules arrive. `plan(ids)` answers **waves**: the theme bundle first (vars, then globals — an edge like any other), then the priors in arrival order, then the graph by Kahn's rule. A wave is every remaining node whose dependencies all sit in earlier waves, so a wave may load in parallel precisely because nothing in it is waiting on anything pending. |
| **`CssLoadProcedure`** | How sheets arrive. Append every node's sheet under `media="not all"` wave by wave — fetched, `load` fires, *not applied*; a wave starts only when the previous has landed; a node in flight is shared rather than appended twice — then flip everything to `media="all"` in one synchronous pass. A failed fetch aborts with nothing applied. |
| **`CssHandles`** | The class handles — identity, bound late by the cascade, which is what lets every sheet on the page change while every holder keeps its handle. |
| **`CssClassManager`** | Keeps the graph, the bookkeeping and the API, and is the one place the DOM is touched. `loadCss(group, fallback, subgraph)` resolves the theme through the steward's view — the argument a served module carries is only the fallback — and loads the group's whole tree, dependencies first, applied all at once, so a first load is atomic too. |

**One answer for every group on the page, so a widget mounted later arrives in
the same theme.** Measured on the studio: a first load now lands `StudioStyles`
(the prior) before `MasterDetail`, and `SystemDialog` before the picker's sheet.

### A theme switch without a reload (Wish 0018)

`switchTheme(to)` is the same procedure over every loaded node, then the
outgoing theme retires; `A → B → A` works because leaving a theme forgets it.
The manager follows the store, so a pick here or in another tab that resolves to
a theme other than the one worn is switched to; a tab pinned by `?theme=` stays
put because the override wins inside `resolve()`.

The picker's `switchToTheme` is three steps **in an order that is the whole
design**: the manager switches (a failure rejects with the page whole and
nothing below runs); the address drops any `?theme=` override in place, no
history entry; the pick is remembered *last*, so the manager's own store-follower
resolves to the theme the page already wears and does nothing. Remember before
the address and it would resolve to the stale override and switch back.

**Apply** switches and keeps the dialog open — the same element — so the next
theme can be tried. **OK** switches and closes. **Cancel** does nothing. The
theme in use is nothing to switch to, so Apply is off and OK reads Close. The
header label, the dialog's chip and the Themes page's *(active)* row all follow
`onThemeApplied`, so a switch made elsewhere — the workbench, another tab —
shows in each. The `sessionStorage` reopen flag and its two exports are gone:
the reload they papered over no longer happens.

Measured per the wish's own recipe: default → forest in 9 ms; the body
background samples exactly two values — old, then new, no third; the open dialog
is the same element afterwards; `history.length` is unchanged; the six sheets on
the page are the new theme's, in dependency order.

### The CSS graph workbench

A workspace widget beside the party monitor, on RFC 0063's shape: it draws from
the manager's `snapshot()` and `plan()` — frozen data — every group the page has
loaded as a node in **columns by wave**, the order a load or a switch would run
in, with its dependencies, a badge for a prior and one for a node named by a
dependency but never declared, and every sheet with the theme it is under.
**Plan** asks what a switch to the chosen theme would do and says so in the
note — nothing appended. **Run** performs it and reports the time. The procedure
tells whoever listens as each sheet moves, and the workbench redraws just that
card's sheet line: `…` fetching, `●` landed but not applied, `✓` applied.
Sampled at 1 ms during a switch, the glyph string across ten cards read
`✓●✓●✓●✓●✓…✓…✓…✓…✓…✓` — six sheets of one wave in flight together while the
earlier waves had landed. The waves, visible.

On the studio: ten nodes in five waves — the bundle, `StudioStyles` as the
prior, six independent groups in one wave, then `ThemePickerStyles` behind its
two edges. Provisioned in the studio workspace only, under **Diagnostics**.

### The party can see itself (RFC 0063)

`_DomOpsPartyBase.snapshot()` returns a deep-frozen plain-data projection of a
branch and everything under it — name, depth, path, owner label, owner liveness,
elements, branches — holding no function and no reference to any live branch or
element. **A holder can inspect the tree and cannot touch it.** That is the whole
contract: a monitor *inside* the tree it renders must not hold the handle that
could dissolve its own host, and `getBranch()` hands out exactly that handle.
Observation by construction rather than by manners.

`viewParty()` is exported, and it is the **only** thing a monitor imports. The
RFC's own D4 had the monitor import `domOpsParty` and call `snapshot()` on it —
which puts the root handle in the widget's closure; a frozen snapshot protects
nothing then. `viewParty` closes over the root inside the party module and hands
out only the projection.

**`activate(owner, label = String(owner))`** separates who is watched from what
it is called. Welded together, the owner had to be something with a presentable
`toString`, which is exactly why every call site minted a labelled sentinel
instead of passing the thing that actually owns the branch — and a minted
sentinel is collected at the first GC. Uncoupled, `wBranch.activate(tab,
'widget:' + uuid)` becomes possible: the tab is what MTP retains for the tab's
lifetime; the label is what the monitor shows. `ownerLabel` is *captured* at
`activate()` rather than derived from the `WeakRef`, so it survives the owner —
a leaked branch is precisely one whose owner can no longer be dereferenced, and
precisely the one whose name matters most.

**The Party Monitor** (🧬, under Diagnostics in the studio workspace,
`SINGLETON`) is the chrome and one `TreeRenderer` per snapshot. A snapshot is
immutable, so a refresh is a new tree, not a mutation: a fresh renderer in a
fresh sub-branch, the previous dissolved. `PartyMonitorAdapterModule` is pure — a
branch becomes a row whose children are its elements as leaf rows followed by its
sub-branches, so the party and what it owns read as one tree; depth and the
collected mark in the badge, the owner label in the note. The monitor outlines
its own row through the adapter's path — the honest proof the view is live.

The note under the header never says "no leaks". It says *"N owners collected"*,
because until D14 holds at every activation site the two are not the same
thing, and today they are not.

This is the base's **first direct test**. The party was exercised only through
rules that check its *use* and stubs that stand in for it. Eight cases now, and
the leak case is not vacuous: the engine collected the owner after one GC pass
and the label was read back after.

### What the monitor found: the import chain was forked

On its first spawn the monitor drew root alone — one branch, no elements, no
self-highlight. Two `DomOpsPartyModule` instances were loaded: the chrome's as
`…&theme=default&locale=en-US`, the renderer's bare. **A module's imports
inherit the query its own request carried**, so everything under the chrome was
keyed by that URL; `WidgetEntriesJson` minted a widget's `moduleUrl` bare, so a
widget started a *second* chain — a second instance of every module the chrome
already held. Duplicated code for a stateless module; for a singleton-bearing
one, a second and empty root. `DocTreeWidget` imported the party the same way,
and whatever it did with it had been happening in a shadow tree. Nothing could
see this before there was a tree to look at.

Fixed at the one place a widget is imported. **`ServingContextModule`** reads
`import.meta.url` — the one honest source, since it is imported by the chrome's
chain and so carries the chrome's query — and `WidgetMounter.resolve` carries
that onto `entry.moduleUrl`. After the fix: one `DomOpsPartyModule` instance,
thirteen branches, 999 elements, the monitor outlining itself with its own tree
sub-branch drawn beneath. (With RFC 0064 the module chain is bare anyway; the
fix stands because the mechanism was wrong, not because the key was.)

And what the first snapshot found: nearly every branch reported as leaked —
including the root, whose owner the source called *"module-scoped, never
GC'd"*. **The comment was false.** V8 does not retain a module-level `const`
that is neither exported nor captured by a closure. The root now owns itself —
`domOpsParty.activate(domOpsParty, 'partyChief')` — because there is nothing
above the root and it cannot dissolve, so "owned by the party" is the truth
rather than a sentinel standing in for it. Verified alive after eight rounds of
forced allocation pressure.

### The picker shows a page, not swatches

A theme is shown by wearing it. **`ThemePreview`** (`/app?app=theme-preview&theme=`)
is a headerless page carrying the studio's own elements — kicker, title, cards,
status badges, a progress bar, a listing, a task list, a table, a footer —
rendered under whatever theme the address names, which the steward reads as that
page's override. The picker's content pane embeds it in an iframe and points it
at the selected theme on every selection, keyboard or mouse; the frame is one
element whose address changes, and re-selecting the shown theme is free. A
loading banner shares the frame's rectangle — faded rather than removed,
transparent to the pointer, so a fast load barely registers and a slow one reads
as on its way rather than broken; `load` fires for error pages too, so it cannot
get stuck.

The dialog asks for 1100×780, and **`SystemDialog` now clamps a requested size
to the viewport less a margin** — a dialog that asks for more than the screen
has gets the screen, not an overflow. The swatch strip and its two classes go;
`tp_inline` widens from 340px to 760px so the Themes page's inline picker can
show a page rather than a sliver.

### Brutalist

A riso-print order form as a studio theme: ink on paper over a grid, 4px rules,
zero radius, solid offset shadows, one loud yellow, blue links and a red edge.
**Every rule rides on `@layer theme` and touches only classes the studio already
renders — no module, no markup, no script.** Cards, rows, panels and pills press
into their shadow on `:active` and lift on hover, with `steps(2)` so it snaps;
filters, dialog actions and the shell's buttons share one button grammar with a
hatched disabled state and a blue `:focus-visible` ring; the search field
inverts to yellow on focus; the kicker becomes the rotated yellow stamp. Dark
mode swaps ink and paper — the shadows go white, the yellow stays.

What CSS could not reach is recorded on the class: the shared tree's rows are
inline-styled by `TreeRendererModule` and keep their soft selection tint under
every theme. The eleventh theme, in the Expressive group.

### The workspace group is the leaf, the kind is the anchor (RFC 0058, Phase 1)

A **`WorkspaceGroup`** — id, title, summary, default kind, the specs it holds —
is the unit of placement. A studio places one as an ordinary catalogue leaf, and
the kinds it holds are never leaves themselves: a kind is a path inside it,
`#ws/<section-slug>/<kind>`, which the server never sees.

```java
WorkspaceGroupRegistry.INSTANCE.register(WorkspaceGroup.of(
        "conformance", "Conformance",
        "The module Navigator plus Summary, Full Content, and Conformance panes.",
        List.of(ConformanceWorkspaceSpec.INSTANCE)));

// placed once, like any leaf
Entry.of(this, new Navigable<>(WorkspaceGroupApp.INSTANCE,
        new WorkspaceGroupApp.Params("conformance"),
        "Conformance Workspace", "The module Navigator plus …"));
```

**Two apps, on purpose.** `GenericWorkspace` — `?ws_kind=`, the whole registry
inlined, kind switching through `/goto` — is the flat address every pre-0058
link carries, and it stays exactly as it is: a permalink is a permalink. Nothing
in it knows groups exist. **`WorkspaceGroupApp`** (`?ws_group=<id>`, required,
nothing else) hosts `WorkspaceGroupChrome`: the group from the param, the kind
from the anchor else the default, canonicalised in place, a notice for a `ws/`
anchor that lied, the inner crumbs appended after the stamped trail, and a
reload on `hashchange`. A studio that has not placed its groups is not broken,
only unpositioned.

The group validates its tree at construction, in the register of RFC 0051's
boot laws: every kind registered and every section slug unique; the default a
member; a kind's segment its id. The fourth law spans groups and the catalogue,
so it lives in `WorkspaceGroupRegistry` (a kind in two groups is refused) and
`WorkspaceGroups.assertPlacedOnce`, which walks a studio's L0 root so a group
placed twice, a group placed nowhere, or an unregistered group each fail the
boot with the names. A kind that a group holds must not also be a legacy leaf;
a legacy leaf on its own is unpositioned, not wrong.

**The legacy kind counts only where the server stamped it.** The chrome read
`ws_kind` from the params `StandardMPA` hands a widget — the *union* of the
request's query and the stamped params — so `/cat/…/workspaces?ws_kind=sales`
would have opened sales on an authentic address, a second way to name a kind
where the anchor is meant to be the one. Two closures: the codec makes the two
forms exclusive, and the page handle exposes the stamped params alone.

Three seams underneath, each reusable: **`StandardMPA` passes a page handle as
every widget mount's fourth argument** (`page.params`, the server-stamped value
alone; `page.extendCrumbs(more)`, which continues the stamped trail and never
replaces it); **`HrefManager` gains `hash`, `onHashChange`, `replaceHash`,
`replaceParam` and `reload`**, the one place `window.location` may be read; and
`WorkspaceSpec.group()` is renamed **`section()`** — a *group* is the container a
studio places, a *section* is a heading inside it. The switcher serves both
apps: a group means anchor mode; `availableKinds` plus `switchBase` means goto
mode.

### Conformance: no exemption by category

The RFC 0045 fix made `PRIMITIVE` rule-identical to `CONSUMER`, but three
channels still granted an exemption to anything that looked like a primitive,
none of them a decision anyone wrote down:

- **`no-raw-css` fired only when the CSS manager was injected** — only if the
  module imported a `CssGroup`. The modules that don't are exactly the
  primitives: `SplitPane`, `MultiTabPane`, `MTPDrag`, `Modal` and the grid layout
  family each mint their own `<style>` element and write `className` raw, and
  passed green. **74 raw class ops in 10 modules were unpoliced.** The rule is
  ungated now, like `no-inline-style`, and a `<style>` element minted from JS is
  itself a finding. `CssClassManager` is the one explicit `Allowance`: it is
  where the typed path ends.
- **`extendedWith` accepted any rule set for a downstream type**, including one
  with no DOM rule at all. The demo's `GAME_LOOP` was a live case: a module with
  sixteen inline style writes held to a frame-rate rule. An extension rule set
  must now sit in a **lane** — the full DOM-owner discipline, or
  `NoDomAccessRule`, plus the globals — and `CompositeJsRulePolicy` refuses one
  that sits in neither. `DefaultJsRulePolicy.domOwnerLane` / `headlessLane` build
  one.
- **`CrateEntry.of` accepted a declared mechanical type**, so a first-party
  module could hand itself the bundled external's empty rule set. Only a domain
  role can be declared now.

And **the baseline is held to what it claims**: every fingerprint must match a
live finding, so a deleted module or a fixed violation fails the gate instead of
silently carrying a grant. 33 stale lines went (`PinnedTabSpawner`,
`DocBrowserRenderer`, `TreeAppHost`, six `ParamsWriter` reads); 74 `no-raw-css`
lines came in as the pre-existing debt they are. Later in the release the same
check is why retiring the three backdrop modules took their 91 lines with them
— the stale-fingerprint check would not let them stay.

## Fixes

**Maple Bridge and Retro 90s were broken by the steward, and are repaired by
retiring their backdrops.** The server no longer knows the theme a page wears,
so their framework-injected SVG backdrops never rendered — while their globals
still installed the universal `pointer-events: none` plumbing those backdrops
needed. A page dead to the mouse except for a whitelist. Both keep their
palettes and lose the backdrop: a fixed gradient is the page surface now —
Maple Bridge's night sky in literal navy, Retro 90s' teal mixed from its own
surface token so it dims with the dark-mode override. The scanlines still draw.
The illustrated, per-element-interactive background is the subject of a later,
proper design.

**Jazz Drums leaves the registry and the crate.** The experiment in putting a
complex interaction into a background worked and was too attractive; it goes
rather than being kept going on a mechanism the release just removed.

**The workbench collapsed to a sliver in a tab.** A widget host has no height of
its own, so the columns' `flex-basis: 0` collapsed them to a scrollbar — a graph
drawn and invisible. `flex: 1 1 auto` sizes them by content there and fills the
rest where the host has a height.

**`href.withParam` now keeps the fragment.** RFC 0058 put the workspace kind
there, and a param written onto the address was dropping it.

**The `TreeRenderer` caret is 18px/21px, from 10px/12px.** It was easy to miss
against the row in the navigator and every other `TreeRenderer` tree; the party
monitor made it visible by drawing fourteen of them in a column. The line is
inline style — `TreeRenderer`'s baselined debt, since it lives in `homing-core-js`
and cannot reach a studio sheet — and the two baseline entries that match on
that line's exact text move with it. Same debt, same count.

**Brutalist: an inert button under the pointer stays put.** The hover rule
outranked the disabled class by specificity and would have lifted it. A
disabled action keeps its hatching, no lift, no shadow.

## Breaking changes

- **`CssGroup.cssImports()` is removed, and so is `CssImportsFor.none()`.** Every
  `CssGroup` implementation overrides it — it was abstract — so **every
  downstream group will fail to compile** until the override is deleted. The
  fix is a deletion; the group's dependencies are now derived from its classes'
  `dependsOn()`. A group whose classes lean on another group's classes should say
  so on the class:

  ```java
  // before — on every group, almost always this
  @Override public CssImportsFor<MyStyles> cssImports() {
      return CssImportsFor.none(this);
  }

  // after — nothing on the group; on the class that actually leans on another
  public record my_body() implements CssClass<MyStyles> {
      @Override public List<CssClass<?>> dependsOn() {
          return List.of(new MasterDetailStyles.md_body());
      }
  }
  ```

  A group that listed an import and has no class that says `dependsOn` anything
  in it now has no edge — the correct answer if the rules really are independent,
  and a load-order regression if they were not; the workbench will show the
  missing edge. `CssClass.groupOf` reads the enclosing group's `INSTANCE` by
  declared field, so a `CssClass` must be nested in its group and the group must
  carry a static `INSTANCE`.
- **`CssGroupResolver` runs when a group module is served, and refuses two
  things**: a dependency cycle (named in walk order) and a `prior()` group with
  dependencies. Neither can have existed under the old model, so this is a new
  way to fail, not a change to a passing case.
- **The server no longer reads `?theme=` or `?locale=`.** `AppHtmlGetAction`
  serves every page under the registry's default theme; the address's `?theme=`
  is honoured by the client as that page's override. Consequences a downstream
  should check:
  - `Theme.backdrop()`, `backdropInteractivity()` and `audio()` are still
    rendered by the server, which now only ever sees the default theme. A
    downstream theme that declares any of them will not get them unless it is
    the registry's first theme. The two shipped themes that had backdrops lose
    them (above); the two that declare audio keep the declaration and it is
    inert until the client owns it.
  - Module URLs no longer carry `&locale=`. A module that read locale off its
    own URL should ask `PreferenceViewInstance.resolve("locale",
    navigator.language)`.
  - Every CSS group module is served with the theme argument set to the
    registry default. The client's manager treats it as a fallback only.
- **`HrefManager` no longer stamps `?theme=` and `?locale=` onto links.** A
  studio that relied on a themed link staying themed across navigation now gets
  that from the steward instead — for the reader who *chose* the theme. A link
  that must pin a theme for whoever follows it writes `?theme=` explicitly
  (`href.withParam`).
- **`HomingJazzDrums`, `HomingJazzDrumsBg`, `HomingMapleBridgeBg` and
  `HomingRetro90sBg` are removed**, with their SVG resources. A studio that
  registered Jazz Drums by class will not compile; one that stored
  `"jazz-drums"` as a `ThemeName` will resolve it to nothing.
- **`ThemePickerModel` loses `rememberPickerOpen` and `pickerReopenWanted`**
  (the reload they served no longer happens) and gains `previewUrl`.
  `ThemePickerStyles` loses `tp_swatches` and `tp_sw`, gains `tp_preview_pane`,
  `tp_preview_wrap`, `tp_preview_frame`, `tp_preview_loading` and
  `tp_preview_loading_on`.
- **`CssClassManager` now imports four affiliates** (`CssHandles`,
  `CssDependencyGraph`, `CssLoadProcedure`, `PreferenceSteward`) and its
  `loadCss` takes a third argument. Generated group modules already pass it;
  hand-written callers of `loadCss` must.
- **`WorkspaceSpec.group()` is renamed `section()`**, and the wire field
  follows. A spec that overrides `group()` will not compile. Same default, same
  meaning: the heading a kind sits under in the switcher.
- **`StandardMPA` passes a fourth argument to every widget mount.** A mount
  function that declared three parameters is unaffected; one that validated its
  arity, or a harness that stubs the mount, sees `(branch, host, params, page)`.
- **`WidgetMounterModule` takes `servingContext` as an injectable** alongside
  its importer, and a widget's `moduleUrl` is now resolved against the chrome
  chain's own URL. A harness that mounts widgets through it supplies the context
  the way it supplies the importer.
- **`DomOpsPartyModule`'s `activate` takes an optional second argument** —
  `activate(owner, label)` — and every branch has `snapshot()` and `ownerLabel`.
  Additive. The module now also exports `viewParty`. Nothing outside the party
  should hold the root; a monitor imports `viewParty` and nothing else.
- **The conformance gate refuses three things it used to accept.** `no-raw-css`
  is ungated, so a downstream module that mints its own `<style>` or writes
  `className` raw without importing a `CssGroup` now carries findings; a
  downstream `extendedWith` rule set must sit in a lane; and `CrateEntry.of` with
  `MANAGER_INJECTOR`, `GENERATED_CSS` or `BUNDLED_EXTERNAL` throws. A downstream
  baseline that names a module or a line that no longer produces a finding
  **fails the gate** — stale fingerprints are no longer carried.
- **`SystemDialog` clamps a requested `size`** to the viewport less 48px on each
  axis. A dialog that asked for more than the screen and relied on overflowing
  it now gets the screen.

## Known limitations

- **D14 is not yet held at every activation site.** Nine branches — the
  generated bootstrap, `WorkspaceShellChrome` twice, `PickerTabFlow`,
  `MermaidPlate` and the rest — still `activate` a minted sentinel as owner and
  read *collected* in the monitor. `activate(owner, label)` makes the right owner
  (the tab) passable at every one; converting the sites is the follow-up, and
  until then *"N owners collected"* is the honest count and not a leak count.
- **`TreeRenderer.setData` called twice on one renderer releases nothing.** It
  removes the old rows from the DOM and releases none of them from the branch —
  a sub-branch is the party's unit of release, and a flat branch has none.
  Latent, since every caller calls it once; the monitor sidesteps it by
  construction (one renderer per snapshot). Left as it is until the tree view
  with domain-managed cells.
- **Theme audio is inert.** Maple Bridge and Retro 90s still declare `audio()`,
  and the server renders the audio runtime for the theme it serves, which is now
  always the default. Backdrop and audio wait for a client-side owner, the way
  CSS got one this release.
- **Nothing varies by locale yet**, and nothing reads the steward's `locale`
  resolution but the rule itself. Part 2 of RFC 0064 gives a resource that
  varies by locale a way to name it.
- **A `WorkspaceGroupApp` page carries every group's bytes** while it uses only
  its own; a served `/workspace-group` route needs a seam `DefaultFixtures` does
  not have. Phase 1 is the placement and the anchor; the conformance studio is
  the one placement in this repository, and the starter registers the app for
  the studios that build on it.
- **The 74 `no-raw-css` findings the ungated rule surfaced are baselined debt**,
  not fixed. The primitives that mint their own `<style>` element still do.
- **Brutalist cannot reach the shared tree's rows** — inline-styled by
  `TreeRendererModule`, the same debt as the caret above — so the picker's list
  and the catalogue tree keep their soft selection tint under it.
- **The workbench refreshes on demand**, and on a switch that lands from
  anywhere. A group loaded by a widget mounted after the last refresh is not
  drawn until the next one.
- **The `WorkspaceGroupApp` inherits `StandardMPA`'s fifteen page-script
  findings**, baselined as `GenericWorkspace`'s are.
