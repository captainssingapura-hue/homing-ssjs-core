# Release 0.6.1 — Two-Way Docs, Articulated Tables

A point release — all additive, plus two fixes. The headline is the **rigid-doc
viewer's return path**: scroll the body and the table of contents now follows
you, closing the loop that was one-way before. Alongside it, **relations gain
per-cell articulation** (status colour, alignment, emphasis), and two rendering
/ persistence bugs are put to rest.

## What's in the box

### Bidirectional TOC↔body sync in the doc viewer (RFC 0043)

The rigid-doc viewer already drove the body **from** the table of contents
(click / arrow key → scroll + highlight). It now drives the other way too:
**scroll the body and the TOC's highlight and selection follow.** The reader
never loses their place; the "you are here" indicator stops lying.

| Piece | Role |
|------|------|
| Widget-local **Secretary** | The click-vs-scroll feedback loop is dissolved structurally (RFC 0028's pure `(state, message) → {state, actions}` reducer, hosted locally with no hierarchy): one authority owns the current node, two writers report up (a TOC actor and a scroll-spy actor), and an asymmetry — navigation *scrolls*, the spy only *highlights* — plus one `programmaticScroll` guard field means the loop **cannot form**. |
| `IntersectionObserver` scroll-spy | Declarative: a collapsed subtree's sections are `display:none`, so folding falls out for free. Its `root` is the **detected** scroll container (the workspace pane, or the viewport when standalone), not assumed. |
| `TreeRenderer.selectPath(path, {silent, reveal})` | A new reusable primitive that moves the TOC selection **without** firing `onSelect` — so the scroll-spy can keep the TOC in step without re-triggering navigation (which would re-scroll). Also unifies the keyboard cursor with the scrolled-to node. |
| `renderDocTree(...).dispose()` | The teardown seam for the non-DOM subscriptions `branch.dissolve()` can't reap — the observer and the scroll/`scrollend` listener on an ancestor. The hosts (`DocContentWidget`, `DocTreeWidget`) call it. |

Two refinements landed with it:

- **Keyboard always drives the TOC, never the scrollbar.** The key handler sits
  on the *scroll container*, so as long as focus is anywhere in the doc view,
  arrow keys move the TOC (and the body follows *through* the selection) and can
  never fall back to the browser's default scroll — even after a mouse scroll.
- **Nav scroll targets the detected container explicitly** (`scrollTo`), so it
  works inside a **nested workspace pane**, not only the standalone viewport.

### Articulated relations — per-cell visual enhancement

A relation's cells can now carry visual **articulation** — a status badge,
alignment, and emphasis — authored *in place*:

```java
.articulatedRelation(
    List.of(cell("Module"), cell("Build"), cell("Coverage").right()),
    List.of(
        List.of(cell("homing-core").strong(), cell("passing").success(), cell("94%").right()),
        List.of(cell("homing-shell"),         cell("failing").error(),   cell("71%").right().muted())),
    "Build status")
```

| Piece | Role |
|------|------|
| `cell("…")` (`RelationCell`) | Fluent authoring cell — text plus chained marks: `.success()`/`.warning()`/`.error()`, `.left()`/`.center()`/`.right()`, `.strong()`/`.muted()`. |
| Sparse **side-car** | The marks ride as a `RelationArticulations` structure *parallel* to the plain string `rows`, covering only the cells that need them. The builder derives each `(row, col)` from the cell's position — no coordinates to track (`row -1` = header). |
| Wire + render | The codec emits an `articulations` array **only when present**, so a plain `.relation(...)` is byte-for-byte unchanged; the renderer applies the badge as an inline pill and align/emphasis as cell classes. |

Extensible by design: a new kind of mark is one optional field + one codec key +
one renderer class.

## Fixes

### Embedded SVG / image / table now render in rigid-tree docs

An `SvgDoc` / `ImageDoc` / `TableDoc` embedded **by reference** in a `RigidDoc`
(or `ComposedDoc`) showed *"Failed to load … HTTP 404"* while the doc itself
loaded fine. Cause: `Bootstrap` wired the `/doc-tree` route but not its sibling
`/doc-tree-content` — the endpoint that serves an embedded resource's own bytes,
resolved **by position inside the root doc** (so the embedded doc needs no
separate UUID registration). The route is now registered; embedded resources
serve in every studio.

### Workspace remembers a widget's pane on spawn (Defect 0007)

Opening a widget from any pane **but the first** didn't persist its location — on
refresh it reappeared in the first pane (moving a widget between panes was always
fine). The spawn path recorded a hardcoded root-pane sentinel instead of the real
destination. It now records the true pane path **and** tab index via a new
`MultiTabPane.tabIndexOf(slotId, tabId)` — the tab-strip counterpart to
`paneIdOf` — the same bridge the (working) move path already used.

## Breaking changes

**None.** Purely additive:

- `RelationSegment` gained an optional articulation side-car; its 3-argument
  constructor and the `.relation(...)` builder are unchanged, and a plain
  relation serializes exactly as before.
- `MultiTabPane.tabIndexOf` is a new read-only method — declared in the
  `MultiTabPaneContract` and gated by the conformance test.
- `renderDocTree` gains an optional `autoFocus` input and returns a `dispose`
  handle; existing callers that ignore it are unaffected.

## Known limitations

- **The scroll-spy needs a real scroll container.** A doc short enough not to
  scroll simply never fires the observer — the TOC stays where the last click
  left it, which is correct. The spy's smooth-scroll animation on a nested
  element container relies on the browser's native smooth scrolling.
- **Cell-articulation coordinates are positional** — like the relation's own
  `rows`, they carry no cell ids, so reordering rows/columns moves the
  articulations with the data (a non-issue for inline-authored tables).
