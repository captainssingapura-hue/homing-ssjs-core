# Release 0.7.1 — The Relation Grid, and a Workspace Without Covers

Three efforts land together, and they share a theme: **stop tracking state, and
stop putting layers between the user and the thing they are pointing at.**

**RFC 0050** brings a new module — `homing-relation-grid`, an Excel-like table
built on a typed Relation rather than a free-style sheet. **RFC 0049** rebuilds
the workspace's selection as *recompute, don't track*, replacing a tracked flag
with a total resolver whose invariant holds by construction. **RFC 0052** then
removes the click-capturing cover overlay entirely: the pane under the pointer
is live, a click acts on the widget *and* enters it, and `inert` guards the
rest. Two Issues close along the way. See **Breaking changes** — the workspace's
input model is different in this release.

## What's in the box

### The Relation Grid (RFC 0050)

A new Maven module, `homing-relation-grid`. "Excel-like" here means Excel's
*interaction vocabulary* — ranges, a cursor, deep edit, bulk fill, clipboard —
over a **typed Relation**: rows are tuples with a typed primary key, columns are
entities with an EffectiveType. Excel is free-style with tables as an
afterthought; this is the inverse.

The architecture is the DomOpsParty two-branch model, one level down from the
workspace:

| Piece | Role |
|------|------|
| **Two branches, one visual tree** | The LAYOUT branch owns the `<td>` cell slots and all chrome; the CELLS branch owns every ActualCell for its whole life. A re-render mints fresh slots and *moves* the same cell elements — element identity survives sorts, filters, hide/show and reorder, asserted by a mint counter that never rises. |
| **Placement-only lookup** | `GridViewMaps` is the only place `(i, j)` meets `(PK, columnName)`. Every view operation is therefore a pure remap, and every command speaks identity — never a position. |
| **Detach is not disposal** | A filtered-out row leaves the visible tree but keeps its element, instance and state; it updates while detached and returns current. A cell dies only when its row leaves the Relation. |
| **Selection, one level down** | The workspace's own model re-instantiated over cells: one cursor plus a range list, all shallow, with at most one cell in deep edit. Range state resets on a view remap; the cursor survives by identity, else clamps — so *exactly one cursor* holds through every remap. |
| **EffectiveTypes + a virtual bulk editor** | Bulk editing is value replacement gated by fine-grained types (a `price` is not a `calories` even though both are numbers). Nothing mounts: the session is pure state, cells preview the buffer live, invalid input paints across the whole selection and Enter simply no-ops. |
| **Column sizing + view state (ext2)** | Widths key on `columnName`, so they survive hide, show and reorder for free. Drags are staged (guide line, commit on release), which makes "a resize never cancels an edit" true by construction. Column order, widths, hidden columns, sort and declarative filters serialise as one drift-tolerant `ViewState`. |
| **Header display options** | `header: { show, sticky, includeInCopy, labels }`. `show: false` builds **no** `<thead>` at all rather than hiding one; labels are display-only, so identity stays `columnName` everywhere; `includeInCopy` leads a copied block with its column names. |

Two companion demos ship in the demo repo: the **Dish List** (the baseline case,
whose 23-row operation→mechanism mapping is the acceptance matrix) and a
keyboard-only **Minesweeper** (the boundary case — stateful widget cells whose
moves are *instantaneous* EffectiveTypes, proving the grid is a cell-widget
substrate and not just a table).

**85 tests**, 22 of 23 acceptance rows green (header-click sort is deferred to
RFC 0050-ext1 by decision — the sort command exists and is tested; only its
header affordance waits). The module is conformance-graded from its first
commit; its six reasoned Allowances are documented decisions, not baseline debt.

### Selection resolution — recompute, don't track (RFC 0049)

The workspace used to *track* which tab was active. Now events update a single
remembered **intent**, a **total resolver** derives the definitive selection
from intent plus the live world, and a reconciler enforces it. The payoff is
categorical: a two-glow state is **unrepresentable**, because every trigger
repaints from one resolved answer. A missed event degrades to staleness — cured
by the next trigger — never to corruption.

| Piece | Role |
|------|------|
| **Per-tab `FocusManager`** | 1:1 with a tab, owning the position-independent mechanics: `inert` on its content, focus placement, the `setActive` lifecycle call, and the two declared widget events. Because its listeners live on the tab's own content element, it *travels* with the tab through a re-parent. |
| **The transport modal carries the selection** | Grabbing a tab out is a deliberate act on that tab, so the selection follows it into flight and lands with it on dock — fixing a stale-ring bug where the glow stayed behind. |
| **A drift watch** | Removing a focused node fires no focus event at all — the one drift `inert` cannot prevent. A `MutationObserver`, live only while deep, turns any widget-internal re-render into a reconcile that pulls stranded focus back. This closes **Issue 0003**. |
| **Property-tested** | A 200-event storm (moves, extends, ctrl-clicks, sorts, filters, hide/show, select-all) asserts after *every* step: exactly one cursor, resolving in view, painted classes equal to the resolved answer. |

### A workspace without covers (RFC 0052)

Every non-entered pane wore a transparent overlay that reported clicks to the
shell. It decided nothing — but to *report* a click it had to **intercept** it,
and an intercepted click never reaches the widget. One overlay, three symptoms:
a dead first click on every pane switch, no hover-scrolling, and content the
browser skipped in hit-testing.

The cover is gone. In its place:

| Piece | Role |
|------|------|
| **The pointer is a declaration of intent** | The pane under the pointer goes live (`inert` off); everything else stays dormant. Safe by physics rather than bookkeeping — a pointer cannot be in two panes, and cannot reach another widget without leaving this one. |
| **A click acts *and* enters** | Entry is reported capture-phase, before the browser's focus step, and the event is never consumed — so the same click that enters the pane also presses the button under it. The dead first click is gone. |
| **One locus per input device** | The keyboard has exactly one home (a cursor pane, or an entered widget); the pointer has at most one. They are independent, so **deep survives the pointer wandering** and typing never follows mouse drift. |
| **Native scrolling, nested regions included** | A live subtree means the browser's own innermost-scroller chaining applies — the wheel scrolls whatever is under the pointer, including a widget's own scroll region, with no framework wheel code at all. |
| **An exact focus rule** | Because entry precedes the browser's focus step, any `focusin` on a tab that is *still not deep* is by construction not click-driven — and is bounced. Legitimate click focus is never bounced; `autofocus` and timer-driven grabs in a merely-hovered pane are. No heuristics, no timing window. |
| **Three degrees of selected-ness** | Keyboard cursor < hover < entered — an order read off the `inert` mechanic, not off taste. A pane paints the **maximum** degree asserting on it, which is single and blend-free because the degrees are totally ordered. Two panes can now be lit at once: *working in A, mouse poised over B.* |
| **A keyboard-locus mark** | A small opaque tab under the bar marks where keystrokes actually land — an orthogonal channel, so ownership is read rather than inferred from which ring looks strongest. It is gated on the workspace genuinely owning the keyboard, so it goes dark when focus escapes to page chrome: a locus that cannot receive keystrokes must not claim it can. |

### Two Issues closed

- **Issue 0003** — a deep-mode re-render could strand focus, leaving no keyboard
  exit. Closed by the drift watch above.
- **Issue 0001** — theme-variable completeness is now enforced by a gate rather
  than trusted.

## Breaking changes

This release changes the workspace's input model and the `MultiTabPane` surface.

- **The cover overlay is removed** (RFC 0052). The `cover-click` /
  `cover-dblclick` `onChromeInteract` kinds are replaced by **`pane-hover`**,
  **`pane-press`** and **`chip-click`**. Chromes that interpreted the cover kinds
  must move to the new ones.
- **A background click now acts immediately.** There is no "safety click" any
  more: clicking a control in a non-entered pane operates that control *and*
  enters the pane. This is the point of the change, but it is a real behavioural
  difference for widgets with destructive one-click controls.
- **`setActive(false)` no longer implies "receives no mouse events."** It is now
  purely a lifecycle signal — *you are not the workspace's current widget* —
  decoupled from mouse reachability, since a hovered pane is live.
- **CSS `:hover` fires inside background widgets**, and text can be selected
  there. JS cannot suppress the former; both follow from removing the shield.
- **RFC 0048's focus API on `MultiTabPane` is gone** (RFC 0049). `selectPane`,
  `focusPane`, `cycleTabInPane`, `enterDeep`, `releaseToShallow`, `mode` and
  `selectedSlot` are no longer pane methods: the shell's focus coordinator
  decides and MTP renders. The renderer facet is `paintSelection`, `paintHover`,
  `paintKeyboardScope` and `setAddEnabled`; the access facet is `contentElOf`
  and `neighbourOf`.
- **`FocusScope` is retired** (RFC 0049). Its job moved into the per-tab
  `FocusManager`; the give-up convention itself is unchanged from a widget's
  point of view — an un-consumed Escape still hands the pane back.
- **A chip click now enters deep.** It reports `chip-click` in addition to the
  existing activation event; the keyboard tab-cycle, which shares the same
  `switchTab` path, deliberately still does not enter.

## Known limitations

- **Header-click sort is not in the grid yet.** The sort *command* exists and is
  tested; the header affordance is RFC 0050-ext1, along with per-column
  comparators, filter UI and pluggable headers. Sorting today compares raw
  values, which is wrong for enums carrying a domain order — the comparator
  belongs on the EffectiveType, and that is ext1's correctness fix.
- **The grid is in-memory.** Virtualisation is designed for but not built;
  detach-not-destroy is already the windowing mechanism a streaming Relation
  would need behind the same adapter.
- **The grid ships its own stylesheet**, injected from JS rather than typed CSS —
  a deliberate PRIMITIVE decision (it depends only on `homing-core`), and the
  subject of RFC 0050-ext3, which reframes those classes as a *predicate
  ontology* whose CSS is merely one conforming model.
- **Screen readers get the reading path, not an operable grid.** The grid renders
  a genuine `<table>` with `<th>` headers and an `aria-label`, read with the
  reader's own table commands; `role="grid"` is deliberately *not* declared,
  because a half-correct ARIA grid flips readers out of browse mode and destroys
  the header association we get for free. Revisit under Wish 0003, gated on
  testing with a real screen reader.
- **Three pointer edge cases remain open** in RFC 0052, none blocking: hover
  liveness during a tab drag, a pointer already parked over a pane at page load
  (no `pointerover` fires until it moves — partly self-healing, since every
  workspace trigger resyncs), and AT dormancy when a screen-reader user leaves a
  mouse resting on a pane.
- **The tab-drag controller still measures geometry rather than hit-testing**, so
  removing the cover did not affect drop targeting — but that coupling is
  unverified against exotic layouts.
