# Release 0.6.0 — HTTPS, and Diagrams As Text

A minor-version bump — not because anything breaks (nothing does; it's all
additive), but because **the framework can now serve over HTTPS**, and transport
security is a big enough capability to earn the version. Alongside it, **Mermaid
diagrams render inside any doc** — diagrams authored as text, drawn as SVG.

## What's in the box

### HTTPS — serve any studio over TLS

Turning HTTPS on is a one-liner: swap `DefaultRuntimeParams` for
`HttpsRuntimeParams`. The presence of a TLS config is what flips the bootstrap
from HTTP to HTTPS — there is no separate flag.

```java
// HTTP (unchanged):
new Bootstrap<>(fixtures, new DefaultRuntimeParams(8080)).start();

// HTTPS:
new Bootstrap<>(fixtures,
        HttpsRuntimeParams.pkcs12(8443, "certs/server.p12", "changeit")).start();
```

| Piece | Role |
|------|------|
| `HttpsRuntimeParams` | A `RuntimeParams` carrying `port` + a `TlsConfig`. Two factories cover the common case with no knowledge of the transport's TLS types: `.pkcs12(port, path, password)` (the JDK default container since Java 9 — preferred) and `.jks(port, path, password)`. Advanced operators can build a `TlsConfig` directly (e.g. a vault-sourced keystore). |
| `RuntimeParams.tls()` | New default returning `Optional.empty()` — i.e. plain HTTP. `HttpsRuntimeParams` overrides it. Existing HTTP deployments are untouched. |
| `TlsPreflight` | Resolves and validates the keystore **without starting a server**, so a downstream can check its HTTPS config at boot / in a CLI / in a test and get a clear error instead of a Vert.x bind stack trace. Returns a `TlsValidationReport` (with a certificate validity window), or throws a typed `TlsValidationException` — `WRONG_PASSWORD`, `BAD_FORMAT`, `MATERIAL_UNRESOLVABLE`. A passing preflight reflects exactly what the server will load. |

Both keystore formats — **JKS** and **PKCS#12** — are supported and covered by
tests. The plumbing is backed by the **ja-http `0.1.0`** bump, which brings the
`TlsConfig` / `TlsCredential` / `TlsResolvers` / `TlsValidator` config surface.

### Mermaid diagrams — authored as text, rendered as SVG

A `` ```mermaid `` fenced block in any markdown doc now renders as a live diagram
in the doc-reader.

| Piece | Role |
|------|------|
| `MermaidProxyModule` (`homing-libs`) | A **configurable 3rd-party proxy**: imports the real Mermaid ESM from a default CDN URL and re-exports a small `renderMermaid(id, code) → svg` helper. The one place the external dependency lives. |
| `ExternalModuleUrlRegistry` | Overrides the proxy's URL **once at boot** — for a blocked CDN, an internal mirror, or an air-gapped network: `ExternalModuleUrlRegistry.INSTANCE.override(MermaidProxyModule.class, "https://mirror.internal/mermaid.esm.min.mjs")`. |
| Doc-reader hook | After marked.js parses a page, it replaces each `` ```mermaid `` fence with the rendered SVG — **lazily**, importing the proxy only when a diagram is present, so diagram-free docs never touch the network. If Mermaid can't load (offline / blocked), it keeps the code fence and shows a short note rather than breaking the page. |

## Breaking changes

**None.** Purely additive:

- `RuntimeParams.tls()` has a default (`Optional.empty()` → HTTP), so every
  existing server compiles and behaves exactly as before.
- Mermaid rendering is opt-in by authoring a `` ```mermaid `` block; docs without
  one are unaffected and stay fully CDN-free.

## Known limitations

- **The Mermaid proxy imports at runtime from a CDN by default.** Behind a
  restrictive proxy (e.g. ZScaler) or on a no-egress network the fetch can fail;
  point the override at a reachable mirror. Bundling Mermaid at build time
  (same-origin, no runtime CDN) is feasible but not yet shipped.
- **TLS material is validated at preflight, not rotated at runtime** — a cert
  that expires while the server runs is not automatically reloaded.
