# Release 0.8.1 — Two Dark Themes, Two Real Dialogs, and a Sort That Means Something

Three efforts land, and they share a shape: **each replaces a placeholder that
worked only while the thing behind it was small.** A `<select>` was enough for
ten themes. A floating panel with no keyboard was enough while there was one
workspace kind worth switching to. Comparing raw values with `<` was enough
while every sorted column held a number.

**RFC 0055** makes theme choice a component — a modal tree grouped by a new
`Theme.group()`, with two new themes to exercise it. **RFC 0057** extracts the
dialog itself into `SystemDialog` and rebuilds the workspace switcher on it, so
both of the studio's system modals now take the keyboard, mark the page behind
them inert, and can be operated without a mouse. **RFC 0050-ext6** makes a
column's ordering something the Relation **declares** rather than something the
grid guesses — mandatory comparators, multi-key sorting as a pinned prefix, and
a header affordance to drive it.

Both new themes are **dark**, and that turned out to be the useful part: a dark
theme is a test. Three latent defects in the theme vocabulary — one of them
present in every theme since the vocabulary was written, another reaching a
downstream studio — were invisible while every palette was light-primary. See
**Fixes**.

See **Breaking changes** — the grid's adapter contract gains a mandatory
method, and a public workspace module is gone.

## What's in the box

### Carbon, Turbo C, and a picker to choose them from (RFC 0055)

Eleven themes now, and the tenth is what made a flat option list stop working:
a reader after "something dark" had to already know the names.

**Carbon** — a neutral slate dark theme in the register of a professional tool
rather than a decorated one, after LSEG Refinitiv Workspace and IntelliJ's dark
theme. It is the first theme here that is **dark by identity**: every other
theme is light-primary with a `prefers-color-scheme` override, so its Vars map
is its light face. Carbon inverts that — Vars *is* the dark palette, there is no
light variant, and it declares `color-scheme: dark` so the browser renders
scrollbars, select popups and the overscroll canvas to match. Text is a soft
grey rather than pure white, which still clears roughly 11:1 on the page
surface; white on near-black vibrates over long reads, and long sessions are the
use case.

**Turbo C** — Borland's DOS IDE, in the EGA sixteen. Every colour is one an EGA
card could actually produce, because that constraint *is* the theme. One mapping
carries the whole silhouette: `COLOR_SURFACE_INVERTED` is EGA light grey, so the
studio's chrome band lands as the grey menu strip across the top of a blue page
— which falls out of the existing token set rather than being drawn, and is the
strongest evidence so far that the four surface steps are named at the right
level. Radius is `0px` throughout: a character cell has no corners to round.

**The picker.** The `<select>` becomes a modal tree, grouped by a new
`Theme.group()` — the question a chooser actually asks. Sections read **Neutral,
Nature, Expressive, Retro**, and the order falls out of the registry: a group
appears where its first member does. Nothing pins the grouping; the only inputs
are `Theme.group()` and registry order.

| Piece | Role |
|------|------|
| **A component, not markup in a handler** | `ThemePicker` has its own DomOpsParty branch and its own `CssGroup`. The `<select>` it replaces was CSS and JavaScript wearing a Java costume inside `AppHtmlGetAction` — string content, and therefore invisible to every rule the framework has. It would have failed four of them on the day it was written. |
| **`Theme.inspiration()`** | One line on where a palette comes from, defaulted so nothing breaks, and taken from each theme's own javadoc rather than invented. It rides in the tree row via `TreeRenderer`'s `showNote`. The tree says what a theme **is**; a reactive palette strip beneath says what it **looks like**. |
| **Swatches as data** | Swatch colours arrive through `element.style.setProperty('--tp-sw', v)` — the route RFC 0044 sanctions for data-driven values. Colour is data; everything else about a swatch is design and lives in the `CssClass`. |
| **It survives a switch** | Switching still navigates (live swap is a wish, not this release). A **one-shot** session-local flag carries "the picker was open" across the reload, so from the reader's side the dialog persists across a try. Reading consumes it — a merely persistent flag follows the reader around the studio opening a dialog nobody asked for. |
| **Apply vs OK** | Because switching navigates, the two confirming actions differ by exactly one thing: **Apply** reloads with the reopen flag set so you land back in the picker and try the next one; **OK** reloads without it. Selecting the theme already in use switches Apply off and turns OK into Close. |

**`MasterDetail`** — tree on the left, content on the right — is extracted from
the two surfaces that had independently arrived at the same fifteen lines and
already drifted. `md_nav` sizes declaratively (`width: max-content` between a
190px floor and a 340px ceiling — "max(designed, longest) + padding", said in
CSS), which is what the catalogue's golden-ratio split was approximating without
knowing how wide a tree wanted to be. What differs between the surfaces is only
what the detail draws, and that stays with the caller.

**A title token.** `st_title` painted from `--color-text-link`, and the two only
agreed by accident while every theme was light-primary. `StudioVars` gains
`COLOR_TEXT_TITLE`; nine themes set it to their existing link colour in both
faces, and only Carbon moves.

### System dialogs, and a workspace switcher you can type at (RFC 0057)

The studio had two modals. One of them had become a real dialog and the other
never did, and the difference was not a matter of polish: the theme picker took
the keyboard, scrimmed and inerted the page, sized itself and restored focus,
while the workspace control panel floated with none of that and painted its rows
with `style.cssText`.

**`openSystemDialog(opts)`** lifts everything the picker had to do by hand:

| Piece | Role |
|------|------|
| **Scrim and `inert`, together** | The scrim is the visible half; `inert` is the real half — without it Tab walks straight behind the scrim and a screen reader reads through it. Only what was switched off is restored, so an element already inert for its own reasons is left alone. |
| **Keyboard ownership by mode** | Capture-phase on `document` when modal, bubble on the frame when not. `modal: false` gives the same frame, actions and keyboard model with no scrim and no inert — Escape dispatched outside a non-modal is ignored, Enter inside still fires the primary action. |
| **Golden sizing, measured once** | 1/φ of each viewport axis, clamped to 460–980 × 320–720. Measured at open rather than tracked: a dialog that resized under the pointer while you read it would be worse than one that is right for the viewport you opened it in. |
| **Lit from one token** | An accent border and three shadow layers, every colour mixed from `--color-accent`, so a theme re-lights the dialog by re-binding one token. Carbon glows amber and Turbo C glows Borland yellow with nothing to change. |
| **Chrome that matches the page** | The caption bar takes `--color-surface-inverted` — the same band as the studio header, because a standalone window's caption is the same kind of thing. A `MultiTabPane` strip deliberately does not: a pane is a region of the page, not a window over it. |

**It stands beside `Modal`, not on it.** RFC 0057 left that open and the build
settled it. `ModalModule` is fully baselined at 210 of its 250 effective lines,
mints raw DOM, and injects its CSS from an **unlayered** `<style>` tag — and
unlayered CSS beats layered CSS outright, which is why the picker's glow could
originally only reach `outline` and `filter`, the two properties Modal happened
not to set. On its own branch and its own typed sheet the glow is an ordinary
`border-color` and `box-shadow` again, and the title bar inherits the page font:
Consolas on Turbo C, where Modal's hardcoded `sans-serif` never would. `Modal`
stays exactly what it is — the draggable panel that carries a widget out of a
`MultiTabPane`, and deliberately not modal.

The theme picker is the first consumer and went from **270 effective lines to
198**, doing nothing but saying what goes in the dialog and what its three
actions mean.

**The workspace switcher, rebuilt.** `WorkspaceSwitcher` replaces
`WorkspaceControlModal` with the same constructor and the same
`open` / `close` / `toggle` / `isOpen` / `destroy` surface, so the shell chrome
swaps one symbol.

- **A tree of kinds beside the instances of the selected kind**, and three verbs
  underneath: **Cancel**, **Open in new tab**, **Open**. Nothing navigates until
  you confirm — browsing and opening are different acts. The primary reads
  **Close** when the target is where you already are.
- **Three regions, and Tab cycles them**: kind tree → instance list → the
  create-instance input → the action row → back. Arrows move *within* whichever
  has focus. One key for which region, another for where in it, so the tree can
  never trap you.
- **The workspace title gains a tab stop** and Enter/Space. It was the only way
  to open the switcher, and a `<div>` with a click handler cannot be reached by
  keyboard at all.
- **`WorkspaceSpec.group()`**, defaulted, so kinds can form a tree — the role
  `Theme.group()` plays for the picker. `WorkspaceSpecJson` and the
  `availableKinds` emission carry it.
- **Open in new tab is `HrefManager.openNew`**, which already existed. No
  `window.open`, which `no-raw-href` would forbid for the same reason it forbids
  `window.location`.
- **`HrefManager` gains `current()` and `withParam(name, value)`** — the
  sanctioned way for a component to ask "where am I" and "here, with one
  parameter changed". `no-raw-href` forbade `window.location` outside the
  manager and until now offered no alternative, which is why callers that
  genuinely needed it simply broke the rule.

**What the rebuild found.** On `/cat/workspace` the old modal's kind switch was
a no-op, and always had been: `ws_kind` is a **typed stamped param**, so editing
it in the query changes nothing. A kind change now goes through
`/goto?app=genericWorkspace&ws_kind=…`, which resolves `(app, args)` to the
authentic catalogue path when one exists and to the flat render otherwise.
Same-kind instance changes keep editing the current URL, so a pretty path
survives them.

The old module and its **37 lines of baselined debt** are gone rather than kept
as dead weight.

### Sorting that means something (RFC 0050-ext6)

The grid compared raw values with `<` — right for numbers and accidental for
everything else. Enums ignored their declared order, text sorted by code point,
and nulls landed wherever the comparison fell. Three layers settle it.

**Comparators, on the Relation's meta, mandatory.** `RelationAdapterContract`
gains `columnMeta(column) -> { compare }`. Ordering is a property of the *data*,
declared beside `get()` — the view state sorts through the adapter and has no
path to a cell's `EffectiveType`, which stays the editing gate. There is **no
fallback**: `sortBy` refuses a column without a comparator, with the remedy in
the message, and a restored `ViewState` drops such a sort as drift exactly as it
drops a filter with an unknown op.

`GridComparatorsModule` ships the stock three:

| Comparator | For |
|------|------|
| `compareNumbers` | numeric columns |
| `compareByOrder(options)` | an enum's **declared** order |
| `compareText` | natural order — case- and accent-folded, digit runs by value. Deliberately **not** a locale collator, so the headless GraalVM harness (no Intl-402) orders exactly as every browser does. |

The grid, not the comparator, puts absent values last in **both** directions and
keeps ties in base order — so a comparator never sees `null` or `undefined`.

**Multi-key as a pinned prefix plus one free key.** The sort is a list and rank
is position, under one invariant every verb keeps: pinned keys form the prefix
in pinning order, and at most one unpinned key exists, always last. That free
key is what a plain `sortBy(column)` replaces while the pinned ones survive.
`pinSortKey(column, pinned)` pins or releases; `removeSortKey(column)` closes the
ranks; `sortBy(null)` clears everything; `sortBy([...keys])` sets the whole list.
Restore is drift-tolerant per key and normalises the prefix, so a list saved by a
grid that knew no pins comes back sane. **The wire format needed no migration** —
ext2 had already made sort a list.

**The caret tier's header affordance.** `GridColumnOpsModule` appends an ops slot
to every `<th>` the layout mints, routes header clicks by position exactly as
`<td>` clicks are routed, swallows the one click that merely ended a reorder
drag, and ignores a click on the resize handle.

- **The footprint is constant.** Caret, rank and pin are minted for every
  sortable column in every state; only their appearance changes. The rank is
  absolutely positioned over the caret so it takes no width, and the pin keeps
  its place while hidden via `visibility`. Sorting a column can no longer resize
  it — a header that shifts when clicked reads as broken.
- **The caret is two-way and anchored.** It holds both triangles always, and the
  header cell's own predicate lights one. The slot **floats right** (a float, not
  flex: a `<th>` must stay a table-cell or column alignment goes), so the caret
  sits flush against the padding whatever the label does. Slot order is
  pin · rank · caret, so the pin's reserved place reads as the gap between label
  and caret rather than a hole after it.
- **Keyboard and ARIA.** `Alt`+`Up`/`Down` sort the cursor's column,
  `Alt`+`Shift`+`Up` toggles its pin. `aria-sort` goes on the `<th>`; the caret
  carries `aria-hidden`, since the `<th>` already says this to a reader.
- **Configurable.** `columnOps` defaults to `'caret'`; `'none'` is yesterday's
  grid; `multiKey: false` drops the pin. A column is sortable **iff** the
  Relation's meta orders it. `ColumnOpsContract` documents the seam, and four
  predicates — `hgr-sortable`, `hgr-sorted-asc`, `hgr-sorted-desc`,
  `hgr-sort-pinned` — join ext3's vocabulary.

## Fixes

**Every theme was setting an invalid `color-scheme`.** The page shell ran
`document.documentElement.style.colorScheme = theme`, assigning `"carbon"` or
`"forest"` to a property that accepts only `normal | light | dark | light dark`.
So the browser fell back to light *and* the inline style outranked the
`:root { color-scheme: … }` each theme declares for itself. Harmless while every
theme was light-primary; on the first dark theme it is a bright scrollbar down a
near-black page. Removed — the theme owns this.

**Closing the picker left the page's keyboard dead.** `Modal`'s own ✕ calls
`onClose`, and `onClose` was `modal = null` and nothing else — so the
capture-phase keydown listener stayed on `document` after the dialog was gone.
It kept answering: arrow keys went to the closed picker's `TreeRenderer`, which
handled them happily and called `stopPropagation`, so the catalogue's own tree
never saw a key again. Escape and the trigger ran the full teardown; the ✕ did
not, and the ✕ is what people click. Each ✕ close also leaked one more listener.

**The workspace answered keys under an open modal.** Not an ordering problem —
`ShallowKeyboard`'s scope test already declined keys whose focus sits outside the
workspace. The hole was its fallback: click the scrim, or any part of a dialog
that cannot take focus, and `activeElement` falls back to `document.body`, which
the workspace read as "focus is nowhere, so the key is mine". The rule it was
missing is general: **an inert region must not claim keystrokes.** The scope test
now walks up from its host and declines if anything above it is inert — walked as
a *property* rather than matched as a selector, because `inert` is inherited by a
whole subtree while only the declaring element carries the attribute.

**The keyboard moved the cursor and the viewport stayed behind.** Arrowing past
the visible band left the cursor painted correctly on a slot nobody could see,
which reads as a frozen grid. There was no `scrollIntoView` anywhere in the
grid's fourteen modules — the follow had simply never been built, and both
companion demos are small enough that no row was ever below the fold. Split
along the module-map boundary: selection's resolved answer now carries **where**
the viewport should follow (a move reveals the cursor, a shift-extend reveals the
range's focus, and Ctrl+A or a remap reveal nothing), and layout does the
arithmetic. Native `scrollIntoView({block:'nearest'})` knows nothing about the
sticky header band, so an upward move parked the cursor under it; the same
least-movement arithmetic runs with the band's height taken off the top edge of
the first scrollport only. The follow is gated on the grid actually holding the
keyboard — a background grid that yanks the page out from under someone is a
worse defect than this one. `revealCursor()` is exposed on the facade.

**A heading silently took body-text colour on a downstream theme.** Found by the
merge check: `FinDashTerminal` defines fifteen of the sixteen colour tokens —
every one except `COLOR_TEXT_TITLE`, which did not exist when it was written — so
`var(--color-text-title)` with no fallback was invalid at computed-value time and
colour inherited. Nothing would have caught it: a downstream studio runs no
completeness test over `StudioVars.ALL`. The fallback is the token's previous
value, so it is exactly the old behaviour for any theme that has not adopted it.

**Reopening the picker gave an empty panel.** The dialog reused one branch across
opens, and `TreeRenderer` numbers its rows from zero on every `setData`, so a
second build asked `DomOpsParty` for the same element name twice and threw
mid-render. Each open now mints a fresh branch and dissolves it on close.

## Breaking changes

- **`RelationAdapterContract` gains `columnMeta(column)`**, and it is in
  `METHOD_NAMES`. Every Relation adapter that will be **sorted** must declare it
  and return `{ compare }` for each orderable column. A Relation that is never
  sorted may omit it, as a game board omits `deleteRows`.
- **`sortBy` throws on a column with no comparator.** A grid that sorted before
  will refuse until its adapter declares one; there is no fallback to `<`. A
  restored `ViewState` drops such a sort rather than failing.
- **`WorkspaceControlModalModule` is removed.** Use `WorkspaceSwitcherModule` —
  same constructor and the same `open` / `close` / `toggle` / `isOpen` /
  `destroy` surface, so a shell that mounts it by symbol swaps one name.
- **The `<select>` theme control is gone from the page shell.**
  `AppHtmlGetAction` no longer renders it; the trigger is
  `mountThemePickerButton(host, opts)`, imported from `ThemePicker` and mounted
  by `StudioElements` into the header bar. A studio that builds its own chrome
  and wants the control must mount it.
- **`color-scheme` is no longer set from the theme slug.** It never worked (see
  Fixes), but a theme that relied on the browser's light fallback must now
  declare `color-scheme` in its own Globals sheet.
- **`st_split`, `st_split_nav` and `st_split_detail` are removed** from
  `StudioStyles`, superseded by `MasterDetail`. Nothing in core or any downstream
  studio referenced them.
- **`StudioVars` gains `COLOR_TEXT_TITLE`.** Core themes must define it — the
  completeness gate requires every theme to define all sixteen and none to define
  anything outside the set. A downstream theme need not: `st_title` falls back to
  `--color-text-link`, which is what the token's value used to be.

`Theme.group()`, `Theme.inspiration()` and `WorkspaceSpec.group()` are all
**defaulted**, so no existing theme or workspace spec breaks by their addition.

## Known limitations

- **Theme switching still navigates.** Live swap belongs in `CssClassManager`,
  which appends the themed sheets itself and so owns them; it is a wish, not this
  release. Apply-vs-OK is the honest workaround, not a substitute.
- **Light/dark mode is not choosable.** Nine of the eleven themes ship a
  *complete* sixteen-token dark palette that nobody can see on purpose, preview
  or test, and the two new ones are single-mode by identity — and the picker does
  not yet say which is which. RFC 0056 covers it and is sequenced after RFC 0037,
  because a hand-authored dark map is the wrong first move without the machinery
  to derive one.
- **A workspace kind still has no guaranteed place in the catalogue.** The
  switcher can reach every registered kind, but `/goto` falls to a flat render
  for any kind nobody wrote a leaf for. RFC 0058 is drafted and not built.
- **A column with no comparator still gets an empty ops slot**, whose left margin
  costs it 8px of header width.
- **The grid is still in-memory**, and still ships its own stylesheet injected
  from JS rather than typed CSS — a deliberate primitive decision, and the
  subject of ext3.
- **`SystemDialog` sizes at open and does not track.** A dialog left open across
  a window resize keeps the size it was born with.
- **`Modal` is unchanged and still not modal.** It remains the widget transport,
  with its unlayered stylesheet and its 210-of-250 baselined lines; the two
  components stand side by side rather than one on the other.
